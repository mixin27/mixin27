## 📱 Overview

People who collect things (books, films, games, cards, figures) usually keep track in a spreadsheet, a notes app or their heads. That works until they want to know what a shelf is worth, who borrowed a box set, or whether they already own something they're looking at in a shop.

**Collectra** is a catalogue for those collections. You make collections, add items by hand, by searching or by scanning a barcode, and Collectra fills in titles, covers and descriptions for books, films and games. Each item keeps its condition, location, quantity, purchase price and current value, with a price history, tags and a record of who it's lent to.

It's **offline-first**. Everything lives in a local database, nothing needs an account, and your data can be exported as JSON or CSV at any time. The app is in seven languages (English, Myanmar, Spanish, Indonesian, Japanese, Korean and Chinese) and is published on Google Play and the App Store.

I designed and built it alone: the Flutter app, its shared packages, and a NestJS backend for accounts and sync. The sync side is fully built but switched off in the current release (see [below](#offline-first-with-sync-built-but-held-back)).

## ✨ Features

### 📚 Collections and items

- Collections for books, movies, games or any custom category, in list or grid view
- Items with a cover photo, description, notes, condition, quantity and location
- **Favorites** and a **wishlist** for things you want but don't own yet
- Search and filters across a collection

### 🔎 Metadata and barcodes

- Search **Google Books**, **TMDB** (films) and **IGDB** (games) by title and fill in the item from the result
- Scan a barcode with the camera. An ISBN goes straight to a book lookup
- Metadata assistance can be turned on or off in settings

### 💰 Value

- Purchase price, purchase date and current value for each item
- **Price history**, with a chart of how the value has changed
- A **statistics** screen: portfolio value, items by type and by condition, the largest collection, and favorites

### 🏷️ Tags

- Tag items, then rename, merge or delete tags from one screen
- Apply or remove tags on many items at once

### 🤝 Loans

- Record who borrowed an item, how to reach them, when it's due, and notes
- Active and history tabs, with overdue loans counted separately
- Mark an item returned when it comes back

### 💾 Backup

- Export everything to **JSON**, or items to **CSV** for a spreadsheet
- Import JSON with a preview of what's in the file before anything is written

### ⚙️ Everything else

- Onboarding for first-time users
- Optional push notifications, with a setting to turn them off
- In-app update prompts driven by Remote Config, with optional or required updates per platform
- Crash reporting with Firebase Crashlytics

## 🏗️ Architecture

A Dart workspace (monorepo) with the app, clean-architecture core packages and one package per integration, so each piece can be built and tested on its own.

```text
collection_tracker/
├── apps/
│   └── mobile/                   # Flutter app: features, routing, bootstrap
├── packages/
│   ├── core/
│   │   ├── domain/               # Entities and repository contracts
│   │   └── data/                 # Repository implementations
│   ├── common/
│   │   ├── ui/                   # Design system and glass bottom navigation
│   │   ├── utils/
│   │   └── env/                  # Compile-time API keys (Envied)
│   └── integrations/
│       ├── database/             # Drift schema, DAOs, migrations
│       ├── metadata_api/         # Google Books, TMDB, IGDB clients
│       ├── barcode_scanner/
│       ├── storage/              # Images and secure storage
│       ├── firebase_services/
│       ├── logger/
│       ├── auth_session/         # Token storage (for sync)
│       ├── backend_api/          # Auth client (for sync)
│       └── sync_api/             # Sync transport (for sync)
├── scripts/                      # Build, test and Firebase setup for every package
└── documentation/
```

### Stack

| Layer | Technology |
| :--- | :--- |
| **App** | Flutter, Dart workspace, Riverpod with code generation, GoRouter, Freezed |
| **Local data** | Drift (SQLite): collections, items, tags, price history, loans, and sync outbox and state tables |
| **Lookups** | Dio clients for Google Books, TMDB and IGDB; `mobile_scanner` for barcodes |
| **Firebase** | Crashlytics, Performance, Remote Config, App Check, Cloud Messaging |
| **Backend** (built, not used by the release) | NestJS 11, Prisma 7, PostgreSQL, JWT auth and device sessions |
| **CI** | GitHub Actions for analysis, tests and builds; release APKs attached to GitHub releases |

## 🧠 Engineering Highlights

### Offline-first, with sync built but held back

Every change is written to the local database first. For sync, the same transaction also queues an operation in a **sync outbox**. The operation's ID is `entityType:entityId:operationType`, so editing the same item five times leaves one pending operation, not five.

The sync orchestrator sends those changes and applies the server's in one transaction, with some safeguards:
- it skips a server change for anything that still has a local edit waiting
- it ignores server updates older than the local copy, allowing for small clock differences
- it applies tags before items so links are restored straight away

Network errors get a few quick retries, then a jittered retry time stored in the database, which the app checks again when it comes back to the foreground. Expired access tokens are refreshed once and the request retried.

All of this is behind three Remote Config flags and an authentication check. For the App Store release I went further and **locked accounts and sync off in code**, so a remote config change can't switch on a half-finished feature. The app ships as a fully offline product while the sync work stays in the codebase.

### Metadata lookups that don't hammer the APIs

The `metadata_api` package wraps Google Books, TMDB and IGDB behind one interface. The app's lookup service picks the right source: an ISBN-shaped barcode (10 or 13 digits) goes to a book lookup. Results are cached in memory with time limits and a size cap (5 minutes for searches, 10 for barcodes, at most 120 entries each), so typing a search or re-scanning the same code doesn't send a new request every time.

### A database that has grown with the app

The Drift schema is at **version 8**. Loans, price history and the sync tables were added after the first release, each with its own migration, so people upgrading keep their collections.

### One workspace, many packages

Each integration is its own package with its own tests, and shared scripts run code generation, analysis and tests across all of them in dependency order. API keys for the metadata services are compiled in with Envied instead of living in source. A setup script creates the Firebase config files, so local builds and CI match.
