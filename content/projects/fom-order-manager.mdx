## 📱 Overview

In Myanmar, a lot of retail happens in chat. A shop posts on Facebook, customers message to order, and the details end up spread across Messenger threads, notebooks and screenshots of bank transfers. When the shop grows to a few staff and a couple of delivery riders, nobody has the full picture.

**FOM** turns those chats into orders the whole team can see. Messages from Facebook Messenger, Telegram and Viber arrive in one inbox; staff pick the messages that make up an order and FOM drafts it; the order then moves through confirmation, packing, delivery and payment, with stock, printing, rider cash and reports along the way.

It is a production SaaS that I design, build and run end to end:

- **Web portal** (Next.js) for owners and staff, plus a Fumadocs help site in Myanmar and English
- **Mobile app** (Flutter) on Android and iOS
- **API** (NestJS on Fastify) with PostgreSQL, Redis and BullMQ workers
- **Operations**: Docker images built on release tags, a deploy script that rehearses migrations, and offsite database backups

The product is **Myanmar first**: Myanmar text and digits everywhere, an English switch at any time, and prices typed in Myanmar digits (၁၈,၅၀၀ ကျပ်) understood as numbers.

## ✨ Features

### 💬 Orders from chats

- One inbox for **Messenger, Telegram and Viber**, with unread counts and live updates
- Select a customer's messages and FOM **drafts one order** from them; returning customers are matched by phone as you type
- Quick replies, auto-replies, and saved replies that fill in the customer's name, order number, total and tracking link
- **Live comment orders**: comments on a Facebook Live become draft orders, with stock held until someone confirms
- Chat-to-order reporting: see which conversations turned into orders

### 📦 Orders, payment and delivery

- Clear statuses (new, confirmed, out for delivery, delivered, cancelled), payment method, and paid or COD on every order
- A **tracking link** customers can open instead of asking
- **Printing**: packing labels and invoices, one order or a batch, on paper or a Bluetooth or Wi-Fi thermal printer, from web and the app
- **Rider cash**: record the COD each rider collects and check the end-of-day hand-over

### 🛍️ Products and shop page

- Products with up to two options (size, colour), each combination with its own price, stock and photo
- Confirmed orders take stock; low stock sends a notice
- **Import products from a spreadsheet**
- A public **shop page** with a cart: buyers order by chat or with a delivery form, and the order lands in the inbox

### 👥 Customers

- Customer profiles with order history, totals and duplicate merging
- **Tags** (VIP, wholesale, late payer…) with a fixed colour palette shared by web and mobile
- **Filters** by tags, last order, number of orders, amount spent and township, with a live count
- **Saved segments** the whole shop can open or export, and **bulk tagging** of every match after confirming the count

### 📊 Reports and data

- Daily, weekly and monthly sales and order reports
- Cost prices with **profit and margin** per order and in reports
- CSV exports that follow the same filters as the screens

### 🔐 Team, billing and support

- Staff invites with roles and permissions, email verification by code, and a list of signed-in devices that can be signed out
- Plans paid by **MMQR** through a local payment gateway, free time and promotion codes
- A **public API** with keys for shops that want to connect their own tools
- **Support tickets** inside the product, with screenshots and reply notifications
- An in-product **What's new** feed, per platform and per language

## 🏗️ Architecture

A Turborepo and pnpm monorepo with four apps (API, web portal, help docs, mobile) and shared packages. Every client talks to one versioned REST API; the web portal goes through its own Next.js route handlers (a backend-for-frontend) so tokens stay in HTTP-only cookies.

## 🧠 Engineering Highlights

### Webhooks that never block

Messenger, Telegram and Viber each have their own webhook controller that checks the request's signature or secret token, stores the event and enqueues a BullMQ job, then answers right away. Workers normalise each event into one thread and message model, link it to a customer, and fan the change out to open clients through Redis. A burst of messages during a Facebook Live slows the queue, not the webhook.

### Realtime without long-lived secrets

Clients ask the API for a short-lived **realtime ticket**, then open a WebSocket with it. The socket only carries "something changed" events scoped to the shop; clients refetch through the normal API, so permissions are checked in one place.

### Correct under concurrency

- Business rows carry a **revision** bumped by a PostgreSQL trigger; edits send `expected_revision` and get a conflict instead of silently overwriting a teammate.
- Limits such as tags per customer are enforced under **per-shop advisory locks**, so two staff tagging at once can't exceed them.
- Bulk actions send the count the user confirmed (`expected_total`); if the matching set changed in the meantime, the API refuses and the app shows the new count.

### One filter language for lists, counts, exports and segments

Customer filtering is built once as parameterised SQL over an aggregate of each customer's orders (count, spend, last order, cancelled orders excluded). The list, the live count, CSV export, saved segments and bulk tagging all use it, and keyset pagination cursors are tied to a hash of the filters so a cursor can't be replayed against different ones.

### Audit by default

Database triggers write an audit row for changes to orders, payments, deliveries, customers, tags, segments, channels and billing records, with the acting user taken from the transaction. Set-based operations such as bulk tagging write one summary event instead of thousands of rows.

### A mobile app that works on bad connections

Lists and details are cached in **Drift** per shop and filter, so the app opens instantly and still shows data offline. The UI kit, localizations, network and database layers are separate packages, and the Myanmar and English message files are kept in step by tests.

### Releases that are boring

Production images are built only when a `v*` tag is pushed. The deploy script takes an exact commit, rehearses pending migrations against a copy before applying them, and with `--seed` adds plan features and the release notes that appear in the in-product What's new feed.
