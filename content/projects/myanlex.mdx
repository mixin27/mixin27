## 📱 Overview

Myanmar text breaks the assumptions most text libraries make. Much of it is still typed in **Zawgyi**, a legacy font encoding that reuses the Unicode Myanmar block with different meanings, so the same bytes can be two different texts. Standard Unicode has its own traps: marks that canonical ordering moves, written syllables that don't line up with code points or graphemes, and other languages written in Myanmar script (Shan, Mon, Karen) that look like Zawgyi to rules written only for Burmese.

**MyanLex** is a toolkit that handles these cases one explicit operation at a time. It is built from the language engine outward:

- **`@myanlex/core`**: a framework-independent engine with no web framework, database, network or environment dependencies
- **`@myanlex/application`**: use cases with input limits and ordered batches, usable offline in Node or a browser worker
- **A versioned HTTP API** (NestJS on Fastify) described by an OpenAPI 3.2.1 contract, with API keys, rate limits and quotas
- **SDKs** for TypeScript, Dart and Python, and a **docs site**
- **A developer console** for workspaces, teams, API keys, a playground, billing-grade usage statements and plans

The project is built so its rules can be checked: every behaviour has a written specification, a corpus of regression cases with recorded sources, and a named, versioned profile reported in every result.

[Myanmar Data Review](/projects/myanmar-data-review) is a web app built on MyanLex for inspecting real Myanmar text data.

## 🧰 Operations

Nine language operations, each with one job:

| Operation | Profile | What it does |
| :--- | :--- | :--- |
| **Encoding detection** | `zawgyi-unicode-v1` | Classifies each Myanmar run as Unicode, Zawgyi, mixed or unknown, without changing the text |
| **Encoding conversion** | `cldr-zawgyi-v1` | Converts Unicode ↔ Zawgyi in the direction the caller names; it never guesses the source |
| **Safe normalization** | `unicode-nfc` | Unicode NFC only, never the compatibility forms that can erase distinctions |
| **Syllabification** | `burmese-orthographic-v1` | Splits Burmese into written syllables, losslessly |
| **Orthography validation** | `burmese-orthography-v1` | Checks the order and structure of each syllable's components against Unicode 17, with code-point diagnostics |
| **Transliteration** | `ala-lc-2011-mapping-v1` | Myanmar to Latin using the Library of Congress ALA-LC 2011 table |
| **Tokenization** | `myanmar-script-tokens-v1` | Lossless tokens for mixed Burmese, Latin, numbers, punctuation, whitespace and emoji |
| **Batch syllabification** | `burmese-orthographic-v1` | Many texts in one ordered request, with per-item failures |
| **Batch transliteration** | `ala-lc-2011-mapping-v1` | The same for transliteration |

The boundaries are deliberate. Detection doesn't convert, conversion doesn't normalize, syllables aren't words (this isn't dictionary word segmentation), validation isn't spell checking, and transliteration isn't translation. When an application needs several steps, it calls them in order and can see what each one did.

## 💻 Examples

All outputs below come from running `@myanlex/core`.

### Detection is conservative

```ts
import { detectMyanmarEncoding } from '@myanlex/core';

detectMyanmarEncoding('ျမန္မာႏိုင္ငံသည္ အေရွ႕ေတာင္အာရွတြင္ တည္ရွိသည္။').encoding;
// 'zawgyi': each run has a Zawgyi probability of 1

detectMyanmarEncoding('မဂၤလာပါ');
// encoding: 'unknown', segments[0].zawgyiProbability ≈ 0.54
```

A short string like the second one is too ambiguous to call either way, so MyanLex says `unknown` instead of guessing. Each result also returns the code-point span of every run and the model's probability, so the caller decides what to do.

### Conversion needs a direction

```ts
import { convertMyanmarEncoding } from '@myanlex/core';

convertMyanmarEncoding('မဂၤလာပါ', { from: 'zawgyi', to: 'unicode' });
// { output: 'မင်္ဂလာပါ', changed: true, profile: 'cldr-zawgyi-v1' }
```

### Syllables, tokens and transliteration

```ts
import { segmentBurmeseSyllables, tokenizeText, transliterateMyanmar } from '@myanlex/core';

segmentBurmeseSyllables('မြန်မာစာ');
// မြန် [0,4)  မာ [4,6)  စာ [6,8)

tokenizeText('MyanLex က မြန်မာစာ 2026 😀').tokens;
// MyanLex latin_word · က burmese_syllable · မြန် မာ စာ burmese_syllable
// 2026 number · 😀 emoji [24,25), plus whitespace tokens

transliterateMyanmar('မြန်မာ', { scheme: 'ala-lc-2011' }).output;
// 'mranʻmā'
```

The emoji in the tokenizer example spans one position, `[24, 25)`: MyanLex counts in Unicode code points, not JavaScript's UTF-16 units, where it would take two.

## 🧠 Engineering Highlights

### A core that knows nothing about the web

The first architecture decision record keeps all language behaviour in `@myanlex/core`, which may not depend on web frameworks, databases, HTTP, authentication, environment variables or logging. Because of that rule, the same engine runs behind the API, in a Node script, or in a browser worker with the network turned off. The package checks prove the last case: they install only the packed archives into an empty directory with an empty npm cache, then run all nine operations in a real browser worker after network access is disabled.

### Positions that mean the same thing everywhere

Every span in every result is a zero-based, half-open **Unicode code-point** range. UTF-8 byte offsets and JavaScript UTF-16 offsets differ between runtimes and can split characters outside the Basic Multilingual Plane, such as emoji. Graphemes don't match Burmese written units either. The TypeScript, Dart and Python clients all get the same numbers, and the tests include emoji to keep it that way.

### Detection that admits when it isn't sure

Hand-written Zawgyi rules misfire on Shan and Mon, whose standard Unicode can look like Zawgyi to rules written for Burmese. MyanLex uses the trained Markov model from Google Myanmar Tools, which was trained on several Myanmar-script languages, and classifies each contiguous Myanmar run separately. A run only counts as Zawgyi at a probability of 0.95 or more, and as Unicode at 0.05 or less. Anything in between is `unknown`. Separate runs in different encodings return `mixed`.

### Conversion that won't damage what's already right

Converting a whole sentence in one direction can break the parts that were already in the target encoding. Conversion always takes an explicit `from` and `to`, and an optional `validateSource` check rejects input that detection finds mixed, mismatched or uncertain, rather than returning a half-damaged result. Automatic mixed-text conversion was looked at and deliberately put off until there are reviewed test cases for it. That decision is written up as an architecture decision record.

### Normalization that only does what's safe

The safe profile is NFC only. NFKC and NFKD are left out on purpose, because compatibility mappings can remove distinctions. The specification records the Myanmar-specific effects: the one canonical composition in the block (U+1025 U+102E becomes U+1026 ဦ) and the four marks with non-zero combining classes. Canonical ordering can move the dot below ahead of an asat, so the orthography validator accepts both orders as equivalent.

### Rules written before code

A change to linguistic behaviour updates the specification, the corpus, the tests and the code together. The corpus holds **334 regression cases** across nine datasets. Each dataset records its source, redistribution terms, transformations and review status. `pnpm quality:report` matches every case to its test result and lists the cases still waiting for independent linguistic review. It's explicit that passing the regression set is not a measured accuracy score.

### A platform around the engine

The API adds what a shared service needs:
- workspaces, projects, invitations and **roles built from a permission catalogue**, with ownership transfer
- an **append-only audit log** of every team, key and plan change
- scoped, hashed API keys
- Redis-backed burst limits across instances, and monthly quotas in PostgreSQL
- health and readiness endpoints, and operator-protected Prometheus metrics

The console's **playground** runs operations in the browser engine by default, or through the API with a signed-in project, with private saved runs.

### Usage you could send a bill for

Every admitted request is written to an append-only `usage_events` ledger **in the same database transaction** that reserves it against the workspace's monthly quota counter, so the two can't disagree: a denied request writes neither, and an admitted one writes both or neither. Metering is always on; the enforcement setting only decides whether limits can deny. If a request can't be metered, it gets a 503 instead of being served for free.

A month-close job writes one **immutable statement** per workspace and month: totals, a breakdown by project and API key, the plan in effect, and a `reconciled` flag that checks the ledger against the counter. Database triggers reject edits to ledger rows and statements. Customers can download every billable request of a month as a CSV, which never contains the submitted text, and ledger rows are kept 13 months before cleanup.

### Plans and prices that can't drift

Plans have a monthly fee, request and character allowances, and per-block overage prices, in their own currency as whole minor units. Each plan either refuses requests at its allowance or bills overage up to an optional ceiling, and quota enforcement uses the same rule. A month is priced on the plan in effect at its end, and the charges are stored on the closed statement. Once any workspace has used a plan, a trigger fixes its terms, so a new price means a new plan; an exclusion constraint stops two subscriptions from overlapping. Plans are assigned with operator scripts that write to the audit log. Payment collection comes next.

### One brand source

The logo, wordmark, favicons, PWA and share images, iOS and Android app icons, and README banners are all generated from three hand-written SVGs by one script. The wordmark is outlined to a path, so images don't depend on installed fonts. A test rebuilds everything and fails if the output changes.

## 🚦 Status

MyanLex is a **developer preview**. Beta packages are published:

- **npm**: `@myanlex/core`, `@myanlex/application`, `@myanlex/types` and `@myanlex/sdk` at `0.1.0-beta.0`
- **pub.dev**: `myanlex_dart` at `0.1.0-beta.0`
- **PyPI**: `myanlex-python` at `0.1.0b1`

There's no public hosted API yet, so the HTTP SDKs need a self-hosted deployment. Next on the platform: payment collection and self-service plan changes on top of the priced statements. The local packages work without one. The API and package interfaces aren't stable contracts yet, and independent linguistic review is still a release gate.
